## 1. 개요

### 1.1. 작성 배경 및 목적
선행 리서치에서는 로봇 1000대 조건에서 다섯 가지 렌더링 모드를 비교하고, Canvas·WebGL·Web Worker 방식이 React DOM 방식보다 CPU 부담이 낮다는 결과를 얻었다. 그러나 측정이 로봇 1000대 단일 조건에 집중되어 있었고, 저사양 기기 조건과 Chrome DevTools 프로파일링 결과는 포함되지 않았다.

이 보고서는 선행 리서치에서 제시한 개선 방안이 실제 관제 환경에서 어느 정도 효과를 내는지 **독립 PoC를 새로 구성하여 로봇 50/100/300/500대 조건에서 정량적으로 검증**한 결과를 정리한다. 목적은 세 가지다.

1. 구현 방식(A/B/C) × 로봇 대수(50/100/300/500) 매트릭스로 성능 차이를 수치화한다.
2. Chrome DevTools Performance·Memory 탭으로 메인 스레드 CPU 시간과 메모리를 프로파일링한다.
3. 당사 관제 시스템에 적용할 방식을 추천하고 도입 리스크를 정리한다.

### 1.2. 선행 리서치와의 차이

| 항목 | 선행 리서치 | 본 PoC |
|---|---|---|
| 비교 방식 | 5개 모드 | A/B/C 3개 방식으로 한정 |
| 로봇 대수 | 1000대 중심 (100·500대 보조) | 50 / 100 / 300 / 500대 매트릭스 |
| 측정 조건 | 일반 조건 | 일반 + CPU 4× 제한 + Performance 탭 + Memory 탭 |
| 빌드 | 개발 모드 | production 빌드 (vite preview) |
| 반복 | 1회 | 핵심 조합(500대·CPU 4×) 3회 반복, 중간값 사용 |
| 저장소 | robot-monitoring | 별도 신규 저장소 robot-render-benchmark |

### 1.3. 테스트 환경
- 기기: MacBook Pro 14인치 (M3), 디스플레이 120Hz, 전원 어댑터 연결 상태
- 브라우저: Chrome 153, 시크릿 창 권장(확장 프로그램 영향 배제)
- 서버: Node.js WebSocket 서버, 전송 주기 10 ms(초당 100회), 로봇 대수는 `ROBOT_COUNT` 상수로 변경 후 재시작
- 클라이언트: React 19 + Vite 8 + Three.js, **production 빌드**로 측정
- 측정 시간: 조합당 10초 (워밍업 300 ms 제외)

### 2.2. 세 가지 구현 방식

표 1. 구현 방식 구성

| 방식 | 구현 | 데이터 수신 | 그리기 | DOM 요소 |
|---|---|---|---|---|
| A (Baseline) | React DOM | 메인 스레드에서 WebSocket 수신, 매 수신마다 setState | 로봇마다 `<div>`, left/top으로 위치 지정 | 로봇 수만큼 |
| B | Canvas 2D + Web Worker | Worker에서 수신·JSON.parse, 16.6 ms마다 최신 배열만 메인 스레드로 전달 | requestAnimationFrame 루프에서 `<canvas>` 하나에 원을 직접 그림 | 1개 |
| C | WebGL(Three.js) + Web Worker | B와 동일 | 로봇마다 Mesh 1개를 생성해 두고 매 프레임 position·material만 갱신, GPU 렌더링 | 1개 |

A는 선행 리서치의 1번 모드, B·C는 4·5번 모드와 같은 구조다. B와 C는 같은 `worker.js`를 공유하므로 두 방식의 차이는 순수하게 그리기 방식의 차이다.

### 2.3. 측정 도구
화면 오른쪽 아래에 측정 패널(FpsMeter)을 두고 다음 지표를 10초 단위로 기록했다.

- 평균 FPS, 최저 FPS, p95 프레임 시간, 최악 프레임 시간, 느린 프레임 수(>33.4 ms), Long Task 수(>50 ms)
- JS heap 최저/최대(`performance.memory`, 측정 중 매 프레임 샘플링)
- **검증 지표**: 수신 로봇 수, 로봇 DOM 요소 수. 수신 로봇 수가 서버 설정과 다르거나, 방식 A에서 로봇 DOM 수가 수신 수와 다르면 경고를 표시해 오염된 측정을 걸러냈다.

결과는 CSV 한 줄로 복사해 `docs/results.md`에 누적했다.

### 2.4. 측정 신뢰성 확보 조치
측정 도구를 검증하는 과정에서 다음 조치를 적용했다.

1. **production 빌드 사용**: 개발 모드는 React 개발용 검사와 StrictMode 이중 마운트 때문에 방식 A가 실제보다 느리게 측정된다.
2. **매 측정 전 새로고침, 초기 모드는 B**: 이전 방식의 DOM 노드·소켓이 다음 측정에 섞이지 않도록 했다. 초기 모드를 A로 두면 새로고침마다 A의 `<div>`가 생성되어 DevTools DOM 노드 수에 잔류하는 문제가 있었다.
3. **워밍업 300 ms 제외, 측정 중 패널 갱신 정지**: 측정 시작 버튼의 렌더링과 패널의 0.5초 주기 갱신이 프레임 시간에 섞이지 않도록 했다.
4. **전원 연결 상태 유지**: 배터리 모드에서는 macOS 저전력 동작으로 FPS가 30으로 제한되는 현상을 확인했다.
5. **핵심 조합 3회 반복**: 500대·CPU 4× 조건은 세 방식 모두 3회 측정하고 중간값을 사용했다.
6. **Performance 녹화 시 Screenshots 옵션 해제**: 스크린샷 캡처 자체가 FPS를 떨어뜨린다.

## 5. 분석

### 5.1. FPS만으로는 부하를 판단할 수 없다
조건 1에서 12개 조합의 FPS는 모두 120으로 같았지만, 조건 3의 메인 스레드 작업량은 A가 B의 5~9배였다. 조건 2에서 CPU를 4배 느리게 하자 숨어 있던 차이가 A의 FPS 붕괴(500대 46 FPS)로 나타났다. **FPS가 같아도 비용은 같지 않으며, 여유 CPU는 관제 화면의 다른 기능(지도, 알람, 목록)과 저사양 기기에서의 안정성으로 직결된다.** 관제 시스템의 성능 기준은 FPS와 함께 메인 스레드 점유율을 봐야 한다.

### 5.2. 방식 A의 한계선
A의 메인 스레드 작업량은 로봇 대수에 거의 비례해 증가했다(50→500대에서 5.4배). CPU 4× 조건에서는 300대에서 CPU 59~86%로 이미 여유가 거의 없었고, 500대에서 90%를 넘기며 평균 46 FPS로 떨어졌다. Layouts/sec가 300대부터 서버 전송 횟수(100회/초)보다 낮아진 것은 프레임 예산 초과로 React 커밋이 병합·지연되기 시작했다는 뜻이다. 선행 리서치에서 1000대·일반 조건의 A가 평균 93.5 FPS를 기록한 것과 같은 현상이다. **A의 실질 한계는 저사양 기준 300~500대 사이이며, FPS 하락보다 CPU 점유율에서 먼저 나타난다.**

### 5.3. B와 C의 비교
B·C는 모든 조건에서 FPS·p95가 동일했고 메인 스레드 작업량도 500대까지 206 ms와 356 ms로 작았다. 다만 **C의 Scripting이 모든 대수에서 B보다 컸다**(500대 323 vs 167 ms). 본 PoC의 C는 로봇마다 Mesh 1개(500개 draw call)를 두고 매 프레임 JS에서 500개의 position·material을 갱신하기 때문에 JS 비용이 대수에 비례한다. 선행 리서치의 1000대 결과(Canvas 6~10%, WebGL 11~23%)와 방향이 같다. **500대 규모에서는 Canvas 2D가 WebGL보다 가볍고 단순하며, WebGL의 이점은 InstancedMesh/Points로 draw call을 1회로 줄인 구현과 수천 대 규모에서 기대할 수 있다.**

### 5.4. 메모리
Heap snapshot은 B 5.1 MB로 고정, A 5.7→8.1 MB, C 6.2→6.9 MB로 대수에 비례해 증가했다. 탭 메모리는 A가 124→146 MB로 비례 증가한 반면 B·C는 50대부터 135~143 MB로 시작(Worker·캔버스/WebGL 컨텍스트의 고정 비용)하되 증가 폭이 작았다. 300대까지는 A가 오히려 10~19 MB 가볍고 500대에서 동등해진다. **500대 규모에서 메모리는 방식 선택의 결정 요인이 아니다.**

한편 B·C의 Worker는 초당 100회 `JSON.parse`로 500개 객체를 생성해 초당 약 5만 개의 가비지를 만든다. Worker heap이 28 MB까지 올랐다가 떨어지는 톱니 패턴과, 조건 2에서 관측된 100~183 ms의 단발성 스파이크(major GC)는 같은 원인이다. 작업 관리자의 탭 메모리는 10초 측정 중에는 상승하는 것처럼 보였으나, 500대 조건에서 2분 연속 관측한 결과 B·C 모두 147~155 MB 범위를 오르내리며 유지되어 주기적으로 회수됨을 확인했다.

### 5.5. 선행 리서치 결과와의 정합성
선행 리서치(1000대·일반 조건)에서 A 93.5 FPS, Canvas CPU 6~10%, WebGL 11~23%였던 결과는 본 PoC의 조건 2·3 결과와 방향이 일치한다. 본 PoC는 여기에 (1) 대수별 증가 기울기, (2) 저사양 조건에서의 붕괴 지점, (3) DevTools 기반 CPU 시간·메모리 분해를 추가했다.
