### 해석

- **500대에서 방식 A가 명확히 붕괴 (3회 모두 재현)**: 평균 46 FPS, p95 26~33 ms(프레임 예산 8.3 ms의 3~4배), 최저 24~29 FPS.
  10초 내내 지속적으로 느린 상태 → 500개 `<div>`의 Virtual DOM diff + left/top reflow가 CPU 4x 조건에서 프레임 예산을 초과.
- **B/C는 500대에서도 p95 9.3 ms 유지 (3회 모두)**: 프레임의 95%는 정상, 평균 118~120 FPS.
- **B/C의 단발성 스파이크는 재현됨**: 10초당 0~1회, 100~183 ms의 긴 프레임이 B 3회 중 3회, C 3회 중 2회 발생.
  heap 최대값이 30~46 MB까지 오른 뒤 떨어지는 패턴과 함께 보면, Worker→메인 스레드로 초당 60회 복사되는 500개 객체 배열(structured clone)이
  쌓여 발생하는 major GC 정지로 추정. CPU 4x 조건에서 GC 시간도 4배로 늘어나 체감됨.
  → 지속적 저하(A)와 간헐적 GC 스파이크(B/C)는 성격이 다름. 보고서에서는 B/C 도입 시 리스크로 기재하고,
  완화책으로 **Worker에서 객체 배열 대신 `Float32Array`를 transferable로 전달(복사·가비지 제거)** 을 제안.
- 300대에서 A는 평균 118.7로 아직 버티지만 최저 40 FPS·최악 25 ms로 흔들리기 시작 → A의 한계선은 CPU 4x 기준 300~500대 사이.
- B와 C 사이에는 500대까지 유의미한 차이 없음 → 이 규모에서는 Canvas 2D로 충분하며, WebGL의 이점은 수천 대 이상에서 기대.
- 50·100대는 모든 방식 동일(120 FPS) → 소규모에서는 방식 선택이 성능에 영향 없음.

#### 해석
- **A의 CPU 점유율은 로봇 수에 거의 비례해 증가**: 50대 14~24% → 100대 27~42% → 300대 59~86% → 500대 89~93%.
  50·100대에서 FPS는 120으로 동일하지만 CPU는 이미 B/C의 5~10배. 즉 FPS가 같아도 비용은 같지 않음.
- **A의 Layouts/sec는 50·100대에서 ~90회**(서버 전송 100회/초에 근접) → 300대 70~93, 500대 41~73으로 감소.
  프레임 예산을 넘기 시작하면 React 커밋이 병합·지연되어 레이아웃 횟수 자체가 줄어드는 것으로, FPS 하락과 같은 현상.
- **B/C는 모든 대수에서 CPU 1~12%, Layouts 0(패널 노이즈 2 제외)** → 로봇 수가 10배 늘어도 메인 스레드 비용 변화가 미미.
- **300대에서 A는 FPS가 아직 118.7이지만 CPU는 이미 59~86%** → FPS만 보면 "문제 없음"으로 보이는 구간에서도 여유가 거의 없음.
  500대에서 90%를 넘으며 FPS가 46으로 붕괴한 것은 이 여유가 소진된 결과. 즉 A의 실질 한계는 FPS 하락보다 앞서 CPU 점유율에서 먼저 나타남.
- 같은 300대에서 B는 2~7%, C는 3~12% → A 대비 약 10배 이상 여유.
- A는 메인 스레드 CPU를 90% 이상 점유. 로봇 렌더링 외 다른 작업(이벤트 처리, 알림 등)을 위한 여유가 거의 없음.
- A의 Layouts/sec 41~73은 서버 전송 100회/초보다 낮음 → 프레임 예산 초과로 React 커밋이 지연·병합되고 있다는 뜻 (평균 46 FPS와 일치).
  매 커밋마다 500개 요소의 left/top 변경 → 전체 레이아웃 재계산(reflow)이 발생.
- B/C는 Layouts 0 (패널 노이즈 제외), Style recalc 0 → DOM 레이아웃 파이프라인을 전혀 사용하지 않음. CPU 10~30%는 Worker 수신 + 그리기 비용.
- B와 C의 CPU 점유율은 500대에서 B 9~33%, C 9~19%로 범위가 겹쳐 이 지표만으로는 우열을 가리기 어려움(B의 상한 33%는 GC 스파이크 순간).
  B·C 비교는 조건 3의 메인 스레드 작업 시간(모든 대수에서 C > B)을 기준으로 함.

#### 조건 3 종합: 작업 합계(S+R+P, ms) 추이

- **A는 대수에 거의 비례해 증가**(50→500대에서 5.4배). 500대에서 메인 스레드의 17%를 로봇 렌더링에만 사용.

- **B는 50→500대에서 40→206 ms**로 완만. Rendering·Painting은 전 구간 12~27 ms로 고정, Scripting만 증가.
- **C는 134→356 ms**. B보다 항상 높으며 증가 기울기도 B보다 큼 → 현재 구현(Mesh 500개 개별 갱신)의 JS 비용 때문.
  WebGL이 Canvas를 이기려면 InstancedMesh/Points로 draw call을 1회로 줄여야 함.
- FPS(조건 1)는 12개 조합 모두 120으로 동일했지만, CPU 시간은 A와 B/C가 5~9배 차이 →
  **FPS가 같다고 비용이 같은 것은 아니다.** 여유 CPU는 관제 화면의 다른 기능(지도, 알람, 목록)과 저사양 기기에서의 안정성으로 직결.
- A의 Painting이 500대에서 661 ms로 가장 큰 항목: 요소 500개를 개별 repaint. B/C는 캔버스 1장이라 19~27 ms.
- 보고서 권장안의 성능 기준은 이 표와 조건 2의 표를 근거로 정함: 일반 조건 작업 시간 비율(위 표) 5% 이하, CPU 4× 조건 Performance monitor CPU 점유율(조건 2 표) 50% 이하.
  500대에서 B·C는 두 기준을 모두 충족(2.1%·3.2%, 9~33%·9~19%), A는 모두 초과(17.2%, 89~93%).

#### 300대 해석
- 작업 합계 A 1,089 ms > C 267 ms > B 167 ms. A는 B의 6.5배, 메인 스레드의 약 10%를 로봇 렌더링에만 사용.
- A는 Scripting 388 / Rendering 379 / Painting 322가 거의 같은 크기 → 요소 수에 비례해 세 단계가 모두 커지는 구조.
  300대에서 FPS는 아직 120이지만 CPU 4x 조건(조건 2)에서 이미 흔들리기 시작한 것과 일치.
- B의 Rendering(14)·Painting(27)은 50대 때와 거의 동일 → 요소 수와 무관한 고정 비용. 증가분은 Scripting(27→126)뿐이며 이는 원을 그리는 arc 호출 수.
- **C의 Scripting(235)이 B(126)보다 큼**: 현재 WebGL 구현은 로봇마다 Mesh 1개(300개 draw call)를 두고 매 프레임 JS에서 300개의
  position/material을 갱신하므로 JS 비용이 대수에 비례. 이 규모에서는 Canvas 2D의 arc 호출보다 무거움.
  → WebGL의 이점을 살리려면 InstancedMesh 또는 Points(1 draw call)로 바꿔야 함. 보고서의 C 리스크·개선안에 기재.
- Heap 패턴: A는 0.5초 주기의 작은 GC(3.9~8.5 MB), B/C는 3~5초 주기의 큰 GC(최대 17~23 MB).
  B/C의 큰 GC가 조건 2에서 관측된 100~180 ms 스파이크의 원인으로 추정됨과 일치.

#### 100대 해석
- 작업 합계 A 576 ms > C 159 ms > B 126 ms. A는 B의 4.6배, 50대(8.5배)보다 배율은 줄었지만 절대량은 A만 크게 증가(343→576).
- A는 Scripting·Rendering·Painting 세 항목이 모두 160~210 ms로 고르게 큼 → diff(JS), reflow(Rendering), 100개 요소 repaint(Painting)가 모두 비용.
- B/C는 Painting 22~25 ms로 A(206)의 1/8. 캔버스 한 장만 다시 그리므로 요소 수와 무관.
- C와 B의 차이는 50대보다 줄어듦(134 vs 40 → 159 vs 126). WebGL 고정 비용의 비중이 감소하는 추세.

#### 50대 해석
- FPS는 셋 다 120으로 동일하지만 메인 스레드 작업량은 A 343 ms > C 134 ms > B 40 ms. A는 B의 약 8.5배.
- A의 Rendering 100 ms(B 5 ms)가 left/top 변경으로 인한 레이아웃 재계산 비용. Scripting 167 ms는 초당 100회 setState + Virtual DOM diff.
- 소규모에서는 C(WebGL)가 B(Canvas)보다 Scripting이 큼(101 vs 27): Three.js의 프레임당 고정 비용(scene 순회, 행렬 갱신, draw call)이
  50개 원을 직접 그리는 Canvas 2D보다 무거움. 즉 WebGL은 소규모에서 이점이 없고 대규모에서 역전될 것으로 예상 → 100/300/500 결과로 확인.

- **Heap snapshot: B는 50→500대에서 5.1 MB로 고정**, 로봇별 객체가 없기 때문. A는 5.7→8.1(+2.4 MB), C는 6.2→6.9(+0.7 MB)로 대수에 비례해 증가.
- **탭 메모리: A는 124→146 MB로 대수에 비례해 증가. B/C는 50대부터 이미 135~143 MB**로 시작(Worker·캔버스/WebGL 컨텍스트의 고정 비용)하되 증가 폭은 작음.
  → 50~100대에서는 A가 7~19 MB 가볍고, 300대 이상에서는 세 방식이 비슷함(차이 5 MB 이내). 그 이상 규모에서는 A가 더 커질 것으로 예상.
- **B/C의 탭 메모리는 10초 측정 중에는 지속 상승하는 것처럼 보였으나, 500대 조건에서 2분 연속 관측한 결과 147~155 MB 범위를 오르내리며 유지됨.**
  즉 GC 주기 사이에 가비지가 쌓였다가 주기적으로 회수되는 톱니 패턴이며, 2분 범위에서 누수 징후는 없음.
  → 리스크 등급 하향. 다만 수 시간 단위 장기 운용은 별도 검증 항목으로 유지. 완화책은 동일(typed array transferable).

#### 500대 해석
- **JS heap은 B(5.1) < C(6.9) < A(8.1) MB**. A가 가장 크지만 차이는 3 MB 수준.
  A의 snapshot에는 로봇 수만큼의 `<div>`·LayoutBlockFlow·ComputedStyle 객체가, C에는 Mesh 객체 501개가 보임. B는 로봇별 객체가 없음.
- **탭 전체 메모리는 세 방식 모두 146~151 MB로 사실상 동일.** 약 140 MB는 브라우저·렌더러 고정 비용이며 방식별 차이는 수 MB.
  B/C는 Worker와 캔버스 버퍼가 추가되어 JS heap 절감분이 상쇄됨.
- **Worker heap은 GC 주기에 따라 0.4 ~ 27.5 MB 사이를 톱니 모양으로 오르내림** (B/C 동일 worker.js, 관측 시점 차이).
  Worker가 초당 100회 `JSON.parse`로 500개 객체를 만들고, 이 배열이 초당 약 60회 메인 스레드로 복사(structured clone)된다.
  Worker 자체의 GC는 Worker 스레드에서 실행되므로 메인 스레드를 멈추지 않는다. 메인 스레드를 멈추는 것은 복사된 배열이 메인 스레드 heap에 쌓였다가
  회수되는 major GC이며(Performance 탭 캡처의 3~5초 주기 톱니), 조건 2에서 관측된 B/C의 100~183 ms 스파이크는 이 GC 정지로 추정된다.
  완화책: Worker → 메인 스레드 전달을 객체 배열 대신 `Float32Array`(transferable)로 바꾸면 복사와 가비지가 거의 사라짐.
- 결론: **500대 규모에서 메모리는 방식 선택의 결정 요인이 아님.** A의 문제는 메모리가 아니라 CPU(조건 2·3).
  메모리 차이는 수천 대 규모 또는 장시간 운용(GC 패턴 차이)에서 다시 검토할 항목.

## 지표 설명

| 열 | 의미 |
|---|---|
| robots | 서버에서 수신한 로봇 수 (= server.js의 ROBOT_COUNT) |
| avgFps / minFps | 평균 / 최저 FPS (디스플레이 주사율이 상한, 예: 120Hz → 최대 120) |
| p95Ms | 프레임 시간 95백분위. 이 값 이하가 95% |
| worstMs | 가장 느린 프레임 |
| slowFrames | 33.4ms(30FPS) 초과 프레임 수 |
| longTasks | 50ms 이상 메인 스레드 블로킹 횟수 (Chrome) |
| heapMinMB | 측정 중 최저 heap. GC 직후 값으로 실사용 메모리에 가장 가까움 |
| heapMaxMB | 측정 중 최대 heap. heapMax − heapMin ≈ 10초간 GC 압력 |
| domNodes | 페이지 전체 요소 수 (참고용) |
| robotNodes | 로봇 DOM 요소 수. A = robots와 같아야 정상, B/C = 0 |
